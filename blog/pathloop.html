Pathloop: Making a Looped MoE Take Different Paths

A looped mixture-of-experts runs the same layers three times. Does it do anything different on each pass?

Chunyuan Deng · August 2026 · project log

TL;DR

We fine-tune a 30B mixture-of-experts model with its middle layers looped three times, which turns 48 layers into 96 executed ones. Looping helps, but not where you would guess: on the coding data we train on it adds nothing, and on the nine benchmarks we never train on it does not raise the peak either — it holds the peak. Plain fine-tuning gains five points out-of-domain and then gives all of them back; the looped runs keep most of theirs. Reading the probes then showed why the loop is weaker than it should be — the second and third passes are near-copies of each other. They route to nearly the same experts and barely change the representation. The loop is not building three different paths through the model; it is building one path and two near-repeats. Pathloop is our attempt to force the passes apart by making the router sample a little during training, and then letting the three passes compete. It is implemented and a first run is in progress.

I. The problem, in plain terms

A mixture-of-experts layer does not use all of its experts. For each token it scores all 128 experts and keeps the best 8. Everything else is switched off. That choice is a hard, discrete decision, and it is the thing we want to study: which experts a token actually passes through is the token's "path" through the model.

Two facts about that path motivate this project.

First, fine-tuning barely changes it. The experts that were not selected receive no gradient at all — they are switched off, so nothing flows back to them. Only the router's scores move, and slowly. A fine-tuning run is far too short to re-arrange routing that was set during pretraining.

Second, looping ought to create several paths but does not. If we run the same block of layers three times, each pass could in principle select different experts and do different work. Our measurements say it mostly does not. That is the finding this log is built around.

II. Method 1: looped SFT, written out

Notation

  • $x = (x_1,\dots,x_T)$ — the input tokens; $d = 2048$ the model width.
  • $L = 48$ — transformer layers, written $T_0,\dots,T_{L-1}$.
  • $[a,b) = [12,36)$ — the looped window; $W = b-a = 24$ layers.
  • $K = 3$ — how many times the window runs.
  • $E = 128$ experts per layer, $k = 8$ selected per token.

One layer

Each layer carries a running state $h$ forward and adds two things to it: attention, then a mixture-of-experts block.

$z = h + \mathrm{Attn}_\ell\big(\mathrm{Norm}(h)\big), \qquad T_\ell(h) = z + \mathrm{MoE}_\ell\big(\mathrm{Norm}(z)\big)$

The mixture-of-experts block is where the path lives. For a single token's state $h_t$:

$s_t = \mathrm{softmax}\big(W_r^\ell\, h_t\big) \in \mathbb{R}^{E}$

$\mathcal{S}_t = \operatorname*{arg\,top-}_{k}\; s_t, \qquad w_{t,e} = \frac{s_{t,e}}{\sum_{e' \in \mathcal{S}_t} s_{t,e'}}$

$\mathrm{MoE}_\ell(h_t) = \sum_{e \in \mathcal{S}_t} w_{t,e}\; f_e(h_t), \qquad f_e(h) = W^e_{\text{down}}\Big(\sigma\big(W^e_{\text{gate}} h\big) \odot W^e_{\text{up}} h\Big)$

  • $W_r^\ell$ — the router: a single matrix scoring all 128 experts.
  • $\mathcal{S}_t$ — the 8 experts this token is sent to. This set is the token's path at this layer. The other 120 experts are not evaluated and receive no gradient.
  • $w_{t,e}$ — how much each chosen expert contributes, renormalised so the 8 weights sum to 1.
  • $f_e$ — one expert: a gated feed-forward network with its own three matrices.

The full forward pass

Layers outside the window run once. Layers inside it run $K$ times, with the same weights each time.

$h^{\text{pre}} = \big(T_{a-1} \circ \cdots \circ T_0\big)\big(\mathrm{Embed}(x)\big)$

Write $F = T_{b-1} \circ \cdots \circ T_a$ for one pass through the window. Starting from $h_{-1} = h^{\text{pre}}$, for $\tau = 0,1,\dots,K-1$:

$u_\tau = F\big(h_{\tau-1}\big), \qquad h_\tau = \begin{cases} u_0, & \tau = 0 \\[4pt] h_{\tau-1} + g_\tau \odot \big(u_\tau - h_{\tau-1}\big), & \tau \geq 1 \end{cases}$

Then the remaining layers run once and the output head is applied:

$h^{\text{out}} = \big(T_{L-1} \circ \cdots \circ T_b\big)\big(h_{K-1}\big), \qquad \text{logits} = W_U\, \mathrm{Norm}\big(h^{\text{out}}\big)$

  • $u_\tau$ — what the window computes on pass $\tau$, before any blending.
  • $g_\tau \in \mathbb{R}^d$ — a learned gate, one value per feature, for $\tau \geq 1$. With $K=3$ there are exactly two gates.
  • Pass 0 is ungated: $h_0 = u_0$, taken in full. Passes 1 and 2 are blended by $g_\tau$, which interpolates between keeping the old state ($g_\tau = 0$) and taking the new one ($g_\tau = 1$).

Executed depth is $a + KW + (L-b) = 12 + 72 + 12 = 96$ layers from 48 layers of weights. Parameter count is unchanged except for the $2d$ gate values; compute per token scales with the executed depth.

Two properties that drive everything later

The gates start at exactly zero. Then $h_\tau = h_{\tau-1}$ for $\tau \geq 1$, the loop collapses to $h_{K-1} = u_0 = F(h^{\text{pre}})$, and the looped model computes bit-for-bit what the original model computes. Training begins from a known-good point. The cost is that the extra passes begin as exact no-ops.

The router weights $W_r^\ell$ are shared across passes. The same router runs $K$ times on different inputs. So the only way pass $\tau$ can select different experts from pass $\tau-1$ is if $h_{\tau-1}$ differs enough from $h_{\tau-2}$ to reorder the top 8 scores. Since $h_\tau - h_{\tau-1} = g_\tau \odot (u_\tau - h_{\tau-1})$, and $g_\tau$ is small early in training, the inputs to the router are nearly identical — and so are its outputs. Section VI measures exactly this.

III. Method 2: pathloop

Pathloop changes one thing during training: how $\mathcal{S}_t$ is chosen. At inference it is switched off and the model is plain top-$k$ again.

Sampling part of the path

Split the budget $k = p + q$. Keep the $p$ best of what the model chose; draw the other $q$ from experts it rejected.

$\mathcal{P}_t = \operatorname*{arg\,top-}_{p}\big\{\, s_{t,e} : e \in \mathcal{S}_t \,\big\}$

$\mathcal{T}^\tau = \big\{\, e \notin \mathcal{S}_t \;:\; \beta(e) = \tau \,\big\}, \qquad \mathcal{Q}^\tau_t \sim \text{sample-}q\big(\mathcal{T}^\tau,\; s_t\big)$

$\tilde{\mathcal{S}}^\tau_t = \mathcal{P}_t \cup \mathcal{Q}^\tau_t, \qquad \tilde{w}_{t,e} = \frac{s_{t,e}}{\sum_{e' \in \tilde{\mathcal{S}}^\tau_t} s_{t,e'}}$

  • $\mathcal{P}_t$ — the $p$ highest-scoring of the model's own 8. With $q=2$ we keep 6.
  • $\beta : \{1..E\} \to \{0..K-1\}$ — a bucketing of the experts, redrawn every step, that assigns each rejected expert to one loop pass. Pass $\tau$ may only sample from its own bucket $\mathcal{T}^\tau$, so the three passes explore disjoint candidates instead of colliding on the same ones.
  • $\mathcal{Q}^\tau_t$ — $q$ experts drawn without replacement with probability proportional to their router score, so plausible experts are tried more often than hopeless ones. Implemented as Gumbel top-$q$: take the $q$ largest values of $\log s_{t,e} - \log(-\log u_e)$ with $u_e \sim \mathrm{Uniform}(0,1)$.
  • $\tilde{w}$ — weights renormalised over the new set, exactly as the unmodified layer would have done for that set.

The token still passes through $|\tilde{\mathcal{S}}^\tau_t| = p + q = k = 8$ experts, so the compute per token is unchanged. What changes is that the $q$ sampled experts now receive gradient, which under plain top-$k$ they never would.

Scoring the passes against each other

The loop already produces $K$ versions of every token's state. We read each one through the model's own output head and score it on the next token:

$R_\tau(t) = \log P\big(y_t \;\big|\; W_U\,\mathrm{Norm}(h_\tau)_t\big)$

$A_\tau(t) = R_\tau(t) - \frac{1}{K-1}\sum_{\tau' \neq \tau} R_{\tau'}(t)$

  • $R_\tau(t)$ — the reward for pass $\tau$ at token $t$: how well that pass's state predicts the true next token $y_t$. Higher is better.
  • $A_\tau(t)$ — the advantage: how much better pass $\tau$ did than the average of its siblings. Because the siblings saw the same token in the same context, this subtracts off everything about the token's difficulty and leaves only the effect of the path taken. No separate baseline model is needed.
  • Note $\sum_\tau A_\tau(t) = 0$ by construction: the advantage says which pass was better, never whether the token was easy.

The two training terms

$\mathcal{L}_{\text{path}} = -\sum_\tau \mathbb{E}_t\Big[\, A_\tau(t)\, \log \pi_\tau\big(\mathcal{Q}^\tau_t \mid h_{\tau-1}\big) \Big]$

$\pi_\tau$ is the router's own probability of having drawn that particular set of $q$ experts, computed as an ordered draw without replacement. Multiplying by $A_\tau$ makes above-average choices more likely and below-average ones less likely. This is the term that turns exploration into learning.

$\mathcal{L}_{\text{ladder}} = -\sum_{\tau} \frac{\lambda\,(\tau+1)}{K}\; \mathbb{E}_t\big[\, R_\tau(t) \,\big]$

Every pass is asked to predict the next token, with later passes weighted more heavily. We use the label rather than a consistency term between passes on purpose: the cheapest way to make the passes agree with each other is to make the loop do nothing, which is the degenerate solution the gates already sit next to. Matching the true next token cannot be satisfied that way.

The full objective is the ordinary fine-tuning loss plus these two, and both are switched off whenever exploration is off, so a run with $q=0$ is exactly plain looped SFT.

Two tiers

  • Tier 1 — sample and measure. Record $R_\tau$ and the spread of $A_\tau$, train on neither. This asks whether the comparison carries signal at all before anything is built on it.
  • Tier 2 — add $\mathcal{L}_{\text{path}}$ and $\mathcal{L}_{\text{ladder}}$.

$q$ follows a schedule rather than being constant, and returns to $0$ before training ends so the final model is trained under exactly the policy it is served with.

IV. Setup

Base model is a 30B-parameter mixture-of-experts with 3B active per token: 48 layers, 128 experts per layer, top-8 routing. The loop covers layers 12–35, repeated three times.

We fine-tune on Ling-Coder, a 400k-example coding instruction set, for one epoch (415 steps). A math dataset (OT3) is the alternative we have also used; everything reported here is Ling-Coder.

We evaluate on 14 benchmarks with greedy decoding. Because we fine-tune on coding data, the benchmarks split into two groups, and keeping them apart turns out to matter more than any single number:

  • In-domain (5) — HumanEval, HumanEval+, MBPP, MBPP+, LiveCodeBench. Coding, the same skill we train.
  • Out-of-domain (9) — GSM8K, MATH500, MATH500-flex, AMC23, AIME24, AIME25, MMLU-Pro, GPQA-Diamond, IFEval. Math, knowledge and instruction-following, none of which appear in the training data.

Splitting the benchmarks changes the conclusion

In-domain, looping does nothing. Fine-tuning lifts coding from 59.6 to about 71, and all three fine-tuned arms land within 0.6 of each other. Whatever the loop contributes, it is not coding ability.

Out-of-domain is where the arms separate, but by less than a final-checkpoint comparison suggests. At its best checkpoint plain fine-tuning reaches 42.7 — a real gain of five points over the base model. Standard-gate looping reaches 43.2, barely ahead. Only the fast-gate arm opens a clear margin, at 45.3.

This matters because comparing final checkpoints tells a much flattering story: there, plain fine-tuning scores 37.5 against 40.3 and 40.9 for the looped arms. That gap is almost entirely plain fine-tuning having fallen back to the base model by step 415, not the looped arms having learned more.

It is retention, not a higher peak

Evaluating at three checkpoints shows what is actually happening. Out-of-domain, every arm peaks at step 149 — the earliest checkpoint we saved — and declines from there. Plain fine-tuning declines all the way back to the base model. The looped arms decline more slowly and stop above it.

VI. What the probes say

We log internal statistics every 25 steps. Two of them reframed the project.

The gates open slowly, and they matter

The router barely moves during fine-tuning

This is the assumption pathloop is built on, and the probes confirm it. Over a full epoch, the routing distribution is almost unchanged:

A full epoch of fine-tuning moves the router by a couple of percent. Routing established in pretraining survives fine-tuning essentially intact — which is exactly why an intervention that forces the router to try alternatives might be worth something.

The three loop passes are not three different paths

This is the measurement that matters most, and the one that reframed the project. The probes are keyed by executed position, not by parameter layer, so all 96 executed layers are recorded separately. Parameter layer $L$ appears at executed positions $L$, $L+24$ and $L+48$ — once per loop pass. Comparing those three tells us directly what each pass does with the same weights.

Why this happens, and why it matters

Pass 0 is ungated and always applied in full, so it does real work. Passes 1 and 2 are multiplied by a gate that reaches only about 0.02–0.06, so they nudge the state rather than transform it. A nudged state produces nearly the same router scores, so it selects nearly the same experts — and the two nudges land in nearly the same place as each other.

This is a problem for pathloop specifically. Its whole mechanism is to compare passes against each other and reward the better one. If the passes are copies, every comparison is between identical things, the advantage $A_\tau$ is zero, and there is nothing to learn from. We confirmed this directly: in short test runs the spread of reward across passes sat at roughly $10^{-7}$, i.e. exactly zero.

It is also a caveat on the claim of "96 effective layers". By this measurement the model behaves closer to 48 real layers plus two cheap refinement passes.

One honest limit on the table above: these are distributional statistics — entropy, top-1 probability, load spread. Two genuinely different sets of 8 experts could in principle produce the same entropy. The statistics being identical to four decimals is strong evidence the passes route the same way, but it is not proof. We have since added a metric that compares the selected expert sets directly, token by token, and reports what fraction of each token's 8 experts carries over from one pass to the next. The current run is the first to record it.

VII. Where pathloop stands

In progress. Pathloop is implemented and unit-tested, and the first tier-1 run on Ling-Coder is training now. No pathloop results yet.

Building it surfaced five bugs, every one silent — nothing crashed, and each would have produced a clean-looking run that measured nothing:

  • The sampled experts were given roughly a third of their correct weight, because two different normalizations were being mixed.
  • The training step counter never advanced under our trainer, pinning exploration at zero for an entire run while the logs reported it as active.
  • The exploration schedule never wound back down, because the trainer does not expose a total step count.
  • Even with that fixed, an off-by-one meant exploration reached zero one step after training ended, so the model never trained under the policy it is served with.
  • The tier-2 auxiliary loss ignored the schedule, so tier 1 and tier 2 differed from step 0 by an amount that had nothing to do with the idea being tested.

The run in progress places exploration in the middle of training — off for the first 100 steps, easing to $q{=}1$, full at $q{=}2$ from 150 to 300, then easing back to zero by 350. The shaded band in Figure 2 shows why: exploring before the gates open would perturb passes that are still doing nothing.

The question this run answers is narrow and prior to everything else: once the gates are open, do the three passes ever become different enough to compare? If the reward spread lifts off the floor, the comparison is real and tier 2 is worth training. If it stays at zero through the exploration window, then the passes are copies no matter what the router does, and the honest next step is not more pathloop but changing how the loop is built — starting the gates away from zero, so the passes are distinct from the beginning.
